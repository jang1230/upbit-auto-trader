## 📚 이전 세션 요약

### 완료된 논의 주제 (7개 / 총 9개)

#### ✅ 주제 1: V3 → V4 마이그레이션 전략
**결론**: Option C (Clean Start with Backup) 채택

**핵심 내용**:
- 기존 V3 설정 파일 자동 백업 (`.v3_backup`)
- 새 V4 설정 파일 생성 (빈 상태)
- 초기 설정 마법사 제공 (빠른 시작 or 수동 설정)
- 언제든 V3로 복구 가능

**이유**:
- V4의 그룹 시스템은 V3와 근본적으로 다름
- 10개 코인을 어떻게 나눌지는 사용자만 알 수 있음
- 처음부터 제대로 설정하는 게 장기적으로 유리

#### ✅ 주제 2: Dry Run 모드 설계
**결론**: 글로벌 설정 + 가상 잔고 영속성

**핵심 내용**:
1. **위치**: 글로벌 설정 (`trading_config.json`)
2. **파일 분리**:
   - `positions_dryrun.json` (Dry Run 포지션)
   - `positions_live.json` (실거래 포지션)
   - `virtual_balances.json` ← 🆕 (가상 잔고, 영속성)
3. **가상 잔고 관리**:
   - 초기 잔고: GUI에서 설정 가능 (기본 1,000,000원)
   - 매 거래 시 즉시 파일 저장
   - 프로그램 재시작해도 완벽 복구 ✅
4. **모드 전환**:
   - 비밀번호 입력 + 경고 메시지
   - 백업 생성 후 전환
   - 프로그램 재시작

**해결한 문제**:
- ❌ 무한 돈 버그 (재시작 시 잔고 초기화) → ✅ 영속성으로 해결
- ❌ Dry Run ↔ 실거래 전환 시 포지션 혼재 → ✅ 파일 분리로 해결

#### ✅ 주제 3: 그룹 관리 제약사항
**결론**: 5가지 제약사항 확정

| 제약사항 | 규칙 |
|---------|------|
| 1️⃣ 코인 중복 | ❌ 불허 (한 코인은 하나의 그룹만) |
| 2️⃣ 빈 그룹 | ✅ 생성 시 허용 / ⚠️ 제거 시 경고 |
| 3️⃣ 포지션 있는 그룹 삭제 | ❌ 불가 (청산 또는 이동 필요) |
| 4️⃣ 관찰 전용 제약 | 포지션 추가 불가, 전환 시 경고 |
| 5️⃣ 전체 제한 | 그룹 최대 50개, 코인 최대 50개 |

#### ✅ 주제 4: GUI 상세 설계
**결론**: 5가지 영역 설계 완료

**핵심 내용**:
1. **메인 윈도우 레이아웃** (1600×850)
   - 11개 컬럼: 그룹|심볼|매수|DCA|익절|손절|평균가|현재가|수량|평가손익|수익률
   - Dry Run 배너 (최상단, 녹색/빨간색)
   - 그룹 필터 드롭다운

2. **그룹 관리 UI**
   - 마스터-디테일 패턴 (좌: 그룹 목록, 우: 코인 체크박스)
   - 그룹 생성/수정/삭제 버튼
   - 즉시 적용 + 저장

3. **그룹 설정 다이얼로그**
   - 프리셋 시스템 (3가지 트레이딩 모드)
   - 자동매수 + 자동매도 / 자동매수 + 수동매도 / 수동매수 + 자동매도
   - 관찰 전용 모드
   - 레벨 설정 버튼 (DCA/익절/손절)

4. **통합 레벨 설정 다이얼로그**
   - 탭 구조: [📊 DCA] [💰 익절] [🛡️ 손절]
   - 프리셋에 따른 활성화/비활성화
   - 각 레벨별 가격 비율, 수량 비율, 실행 옵션

5. **전역 설정 다이얼로그**
   - Dry Run 모드 전환 (비밀번호 + 경고)
   - 리스크 관리 (최대 포지션, 최소 잔고, 일일 손실)

#### ✅ 주제 5: 텔레그램 알림 상세
**결론**: Topic 6 완료 후 테스트 시 설계 예정 (현재는 스킵)

**이유**:
- 실제 에러 상황 확인 후 알림 형식 결정이 더 효율적
- 기본 알림 기능은 이미 구현되어 있음

#### ✅ 주제 6: 에러 처리 및 복구
**결론**: 에러코드 기반 통합 라우팅 시스템

**핵심 내용**:
1. ✅ **Rate Limit 예방** (REST API 이미 구현됨, WebSocket 불필요)
2. ✅ **네트워크 에러 처리** (사용자 인터넷 vs Upbit 서버 구분)
3. ✅ **주문 실패 에러** (잔고 부족 동기화, 최소 주문 금액은 Topic 7)
4. ✅ **WebSocket 재연결 전략** (모든 WebSocket 동일 처리)
5. ✅ **데이터 구조 통합** (trading_config.json 단일 파일)
6. ✅ **API 키 에러 최적화** (시작 시 vs 거래 중)
7. ✅ **통합 에러 핸들러** (19개 Upbit 공식 에러코드 → 6개 카테고리 라우팅)

**최적화 결과**:
- 17/19 에러: 네트워크 체크 생략 (15초 절약)
- 2/19 에러: 네트워크 진단 실행 (timeout, connection_error만)
- 에러코드가 라우터 역할 → 최적 처리 경로 자동 선택

#### ✅ 주제 7: 최소 주문 금액 처리
**결론**: 사전 검증 + 실시간 처리 2단계 전략

**핵심 내용**:
1. ✅ **사전 검증 (GUI 설정 시)**:
   - 가상 시뮬레이션으로 청산 가능성 검증
   - 2가지 문제 감지: (1) 매도 금액 미달, (2) 매도 후 잔액 미달 ⭐
   - 경고 + 자동 해결 방안 (전량 매도 전환) + 권장 수정 방안

2. ✅ **경고 문구**:
   - 익절: "(추가매수 및 손절시에는 변동이있을수있습니다)"
   - 손절: "(추가매수 및 익절시에는 변동이있을수있습니다)"

3. ✅ **실시간 처리 (거래 시점)**:
   - `calculate_sell_amount()` 함수로 최종 검증
   - 매도 불가 시 텔레그램 알림
   - 전량 매도 전환 시 텔레그램 알림 + 상위 레벨 비활성화

4. ✅ **DCA 추가매수**:
   - 검증 불필요 (본인 잔고 관리 문제)
   - KRW 잔고 부족 시 텔레그램 알림만

5. ✅ **일관성**:
   - 익절과 손절 동일한 로직 적용
   - 설정 검증과 실시간 처리 동일한 함수 사용

**주요 함수**:
- `validate_takeprofit_levels()`: 익절 레벨 검증
- `validate_stoploss_levels()`: 손절 레벨 검증
- `calculate_sell_amount()`: 실시간 매도 금액 계산
- `calculate_min_buy_amount()`: 권장 최소 매수 금액 계산
